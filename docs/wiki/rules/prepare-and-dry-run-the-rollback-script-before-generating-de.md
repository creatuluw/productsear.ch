# Prepare and dry-run the rollback script before generating derived rows

**Guideline:** When a bulk data mutation against `te9_dev` is committed for real (no rollback wrapper), write and dry-run-verify the undo script **before** generating any derived data (embeddings, archetypes, content, analysis). Scope the rollback so it can only touch the synthetic rows — for manual inserts that means `id < 0` (see the negative-synthetic-ids convention).

**Pattern used 2026-11-06 for the 522-repo insert (`scripts/rollback-insert-missing-repos-active-30d.sql`):**

- Delete children-first: `bookmark_archetypes` → `bookmark_embeddings` → `bookmark_content` → `bookmark_analysis` (all `WHERE bookmark_id < 0`), then `bookmarks` `WHERE id < 0`.
- Wrap the whole file in a single transaction — all-or-nothing.
- Dry-run it before use: strip BEGIN/COMMIT, wrap in an outer transaction, count affected rows, verify positive-id rows untouched, then ROLLBACK.

**Why:** derived rows are generated by separate scripts after the insert; once they exist, "undo" means knowing every child table in the right order. Having a verified rollback file sitting ready *before* step 2 means any point of failure has a one-command exit. Complements the existing rule on validating the insert itself with a BEGIN…ROLLBACK dry run — that rule proves the insert is safe to run; this one guarantees the committed state is reversible.
